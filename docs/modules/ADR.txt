# Architecture Decision Record: Modal Column Count Tie-Breaking Rule for MalformedRowCheck (FR-5)

---

## Status

- **ADR status:** Final — frozen reference for future module integration
- **Architecture version/reference:** PhenoPred Architecture v1 (Approved)
- **Traceability references:** SRS FR-5, OUT-5, OUT-7, NFR-3, NFR-5

---

## 1. Decision Context

FR-5 requires that "the system shall report the observed column-count distribution across all data rows per file and shall flag rows whose column count differs from the file's modal/expected column count as malformed." Per the Frozen Architecture Clarification Record and Architecture v1 §7.2/§14, this modal count is computed empirically, from the file's own observed `DataRow` collection — never from an externally imposed schema, and never from `HeaderInfo.resolved_columns`. The classification rule that follows is purely mechanical: `len(row.fields) != modal_count`.

This comparison is only well-defined when exactly one `modal_count` value can be identified. FR-5's phrasing ("the file's modal... column count," singular) presupposes such a value always exists, but the row population itself does not guarantee this: when two or more distinct field-count values are observed with equal, tied, maximum frequency, no single value is self-evidently "the" mode. Left unresolved, two independently-built, spec-compliant implementations could each select a different tied candidate and thereby classify a different set of rows as malformed for the identical input file.

This directly implicates NFR-3, which requires that "given the same input file, all structural and data-quality checks... shall produce identical results on repeated execution" — a requirement whose intent, per Stage 1 Engineering Review §11, extends to reproducibility of the specification's outcome, not merely to repeated runs of one already-built binary. An unresolved tie is therefore not merely a coding detail: it is a gap in what FR-5 requires the system to report, and different resolutions would produce materially different, non-interchangeable Findings from the same file. For this reason, the decision belongs at the architecture level — consistent with this project's established practice of freezing exactly this class of decision (as already done for `DelimiterDetector`'s own candidate-ordering tie-break) — rather than being left to an implementer's discretion.

---

## 2. Decision Drivers

The final rule MUST satisfy:

1. **FR-5 compatibility** — must always yield exactly one modal count so that malformed-row classification remains well-defined.
2. **NFR-3 deterministic behaviour** — identical input must always yield an identical outcome, independent of incidental collection iteration order.
3. **NFR-5 schema neutrality** — must not assume or impose any fixed or external schema, and must derive the modal count solely from the file's own observed rows.
4. **Frozen `Finding` contract** — the outcome must still reduce to a single, unmodified `Finding` (`check_name`, `description`, `count`, `examples`, `affected_row_refs`).
5. **`DataRow` and module responsibility boundaries** — the rule must rely only on properties already present on `DataRow`, and must not expand `MalformedRowCheck`'s responsibility into territory owned by `HeaderResolver`, `RowParser`, or any other component.
6. **Independence from unresolved `ColumnCountDistribution` decisions** — this ADR must be fully decomposable from, and must not presuppose an answer to, that separate deferred item.
7. **No hidden assumptions about external schemas or row correctness** — the rule must not encode a claim about which row shape is more "correct," "complete," or "representative."

---

## 3. Considered Alternatives

### Option A: Smallest column count wins
**Advantages:** Simple; deterministic once frequencies are tallied, independent of row order.
**Risks:** Implicitly asserts a narrower row shape is more canonical — an unevidenced claim about data correctness, with no support in FR-5, the SRS, or the underlying notebook observations.
**FR-5 compatibility:** Satisfied mechanically.
**NFR-3 compatibility:** Satisfied.
**NFR-5 compatibility:** In tension — introduces a fixed shape-preference with no evidentiary grounding.

### Option B: Largest column count wins
**Advantages:** Same structural simplicity and determinism as Option A.
**Risks:** Mirror-image risk of Option A — implicitly asserts a wider row shape is more "complete," equally unevidenced.
**FR-5 compatibility:** Satisfied mechanically.
**NFR-3 compatibility:** Satisfied.
**NFR-5 compatibility:** Same tension as Option A, opposite direction.

### Option C: First observed column count wins
**Advantages:** Introduces no magnitude-based claim; reuses `DataRow.line_index`, an already-frozen, positional, invariant-bearing property, and aligns with the architecture's existing ascending original-row-order reporting conventions (`Finding.examples`, `Finding.affected_row_refs`).
**Risks:** Requires precise specification (anchored strictly to `line_index`, never to incidental collection iteration order) to guarantee determinism.
**FR-5 compatibility:** Satisfied — always yields exactly one modal count.
**NFR-3 compatibility:** Satisfied, provided the anchor is `line_index`, not iteration order.
**NFR-5 compatibility:** Fully satisfied — no schema-shape preference introduced.

### Option D: Last observed column count wins
**Advantages:** Structurally identical advantages to Option C — order-based, no magnitude preference, reuses `line_index`.
**Risks:** Same determinism-specification requirement as Option C; additionally, requires deliberately reversing the architecture's existing forward-order reporting convention, with no comparable grounding for doing so.
**FR-5 compatibility:** Satisfied, identically to Option C.
**NFR-3 compatibility:** Satisfied, identically to Option C.
**NFR-5 compatibility:** Fully satisfied, identically to Option C.

### Option E: Explicit canonical ordering (e.g., numeric ascending/descending)
**Advantages:** Mirrors the *format* of `DelimiterDetector`'s frozen tie-break (a fixed, named ordering invoked only on ties).
**Risks:** Not an independent alternative — reduces to Option A (ascending) or Option B (descending) under a different label, inheriting whichever magnitude-preference risk that direction carries.
**FR-5/NFR-3 compatibility:** Satisfied, identically to whichever of A/B it reduces to.
**NFR-5 compatibility:** Inherits Option A's or B's respective tension.

### Option F: Treat ties as unresolved
**Advantages:** Introduces no shape preference of any kind; maximally conservative relative to the "reporting, not resolution" principle.
**Risks:** FR-5's text presupposes a modal count is always identifiable; this option requires inventing an unaddressed new `Finding` outcome category not evidenced anywhere in FR-5, OUT-5, or OUT-7.
**FR-5 compatibility:** Not satisfied as literally written.
**NFR-3 compatibility:** Trivially satisfied, but at the cost of not performing the classification FR-5 requires.
**NFR-5 compatibility:** Fully satisfied, but does not close this decision's scope.

---

## 4. Final Architecture Decision

**The selected rule is Option C — first observed column count wins.**

**"First observed" means:** the tied modal candidate whose occurrence appears at the smallest `DataRow.line_index` among all rows belonging to the tied modal candidate set.

**Justification:**

- `DataRow.line_index` is an existing, frozen positional property — per the RowParser/DataRow approval record, "zero-based, positional index over the sequence of lines RowParser was given," with `line_index >= 0` as `DataRow`'s sole enforced invariant.
- The ingestion/parsing pipeline preserves original row ordering throughout — `RawLineSplitter`, `RowParser`, and `DataRow` all maintain the file's original row sequence without reordering, consistent with FR-14/NFR-2's non-destructiveness requirements extended to in-memory representations.
- Existing `Finding` reporting semantics already use original row order: `Finding`'s frozen docstring requires both `examples` and `affected_row_refs` to be populated as bounded samples "in original row order," and the DuplicateHeaderCheck handoff record confirms `affected_row_refs` is already populated using `DataRow.line_index` directly, in ascending sequence.
- Selecting FIRST extends this already-established ascending-order convention to a new but structurally identical situation — choosing one value from among several equally valid row-derived candidates. LAST would also satisfy determinism (NFR-3) and schema neutrality (NFR-5) equally well, but would require deliberately introducing a reverse-order convention with no comparable grounding anywhere in the frozen architecture.

**This is a deterministic reporting convention, not a judgement about data correctness.** The rule does not claim that earlier rows are more correct, more trustworthy, or more representative of the file's true schema, nor that later rows are less valid. It claims only that, when the data itself provides no basis for preferring one tied candidate over another, extending the architecture's existing ascending-order convention is a smaller, better-grounded step than introducing an unprecedented reverse-order rule would be.

*(Non-essential background: `HeaderResolver`'s own detection logic also happens to check candidates in a defined sequence, but this is a weak analogy — `HeaderResolver` resolves uncertainty about which single candidate is the real header, whereas `MalformedRowCheck` resolves a symmetric statistical tie between candidates that are each equally frequent. This observation is noted only as minor background color and is not part of the justification above.)*

**Rejected alternatives, briefly:** Options A and B were rejected for asserting an unsupported claim about which tied shape is more "correct." Option D was not rejected for unsoundness — it is equally deterministic and schema-neutral — but was not selected because it offers no comparable grounding in existing convention. Option E was rejected as a restatement of A/B. Option F was rejected because it does not perform the classification FR-5 requires and defers the ambiguity into an unaddressed `Finding`-semantics question.

## 5. Formal Rule Specification

### Input

A collection of `DataRow` objects, each exposing:
- `line_index: int`
- `fields: tuple[str, ...]`

### Process

1. Calculate the frequency of each observed field-count value, `len(row.fields)`, across the full row collection.
2. Determine the maximum frequency value across all distinct field-count values.
3. Identify the set of all field-count values tied for that maximum frequency ("modal candidates").
4. If exactly one modal candidate exists, select it as the modal count.
5. If multiple modal candidates exist, select the field-count value belonging to the row with the smallest `DataRow.line_index` among all rows whose field count is one of the tied modal candidates.

The rule's outcome must be independent of dictionary ordering, set ordering, `Counter` insertion behaviour, or any other implementation-specific collection ordering; determinism must derive solely from `DataRow.line_index` values.

### Output

A single selected `modal_count: int`.

**Malformed-row classification:** a row is malformed if and only if `len(row.fields) != modal_count`.

### Worked Example

**Input rows:** line 1 → 5 fields; line 2 → 7 fields; line 3 → 5 fields; line 4 → 7 fields.

**Frequency calculation:** field-count 5 occurs 2 times (lines 1, 3); field-count 7 occurs 2 times (lines 2, 4).

**Tie detection:** maximum frequency = 2, achieved by both field-count 5 and field-count 7 → modal candidates = `{5, 7}` → tie condition exists.

**Selected modal count:** among rows belonging to the tied candidates (all four rows), the smallest `line_index` belongs to line 1 (field count 5). **Selected modal count = 5.**

**Resulting malformed rows:** rows where `len(row.fields) != 5` → line 2 (7 fields) and line 4 (7 fields) are malformed. Lines 1 and 3 (5 fields) are not malformed.

### Resolved:

---

## 7. Testing Implications

The future `MalformedRowCheck` test suite must, at minimum, cover:

1. Unique modal column count (no tie).
2. Two-way modal tie.
3. Multi-way modal tie (three or more tied candidates).
4. Repeated execution produces identical results (NFR-3).
5. Tie resolution independent from dictionary/set ordering — verified via structurally different but logically equivalent input construction paths.
6. Empty input — yields `count == 0`, `examples == ()`, `affected_row_refs == ()`, no exception raised.
7. All rows having identical column count (no tie possible; `count == 0`).
